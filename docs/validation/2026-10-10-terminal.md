# Native terminal payload acceptance — 2026-10-10

Issue: [#16](https://github.com/hackerchai/herdr-relay/issues/16).
Official Herdr 0.9.3 on macOS 27 arm64, isolated Ops instance, actual PTYs
110×34 resized to 132×40, `TERM=xterm-ghostty`, `TERM_PROGRAM=ghostty`.
Compared native local, native with `HERDR_REMOTE_KEYBINDINGS=local`, and the
actual HTTPS/WSS self-host acceptance deployment. The probe and driving scripts
were temporary manual diagnostics outside the repository; no e2e suite was added.

| Check | Native local / remote mode / Cloudflare Relay |
|---|---|
| Initial complete screen with no input | Passed after the TLS flush fix below |
| Bracketed paste with Chinese and emoji | All 50,444 bytes, including framing, identical |
| First SGR mouse down/up after initial screen | Both events delivered at the same pane coordinates |
| Resize | Pane 83×33 → 105×39, matching native layout |
| Kitty inline image | Identical decoded 240×80 RGBA data, 76,800 bytes |
| OSC 52 | Exact 32-byte clipboard payload delivered to a controlled `pbcopy` substitute |
| Native detach | Exit 0 and exact termios restoration in all three cases |

Paste SHA-256: `e75731c6cdf1b7a42c77135f6ec33004c1b668bbe2646918f8409a337d3853ac`.
Image RGBA SHA-256: `ba194701c049cfce81440d13e0ff015751b211051bb517da43c3aee1368d7478`.
Image output uses inline `t=d` chunks; remote mode does not assume a shared
server filesystem. The clipboard substitute verifies native routing without
overwriting the user's desktop clipboard. It does not verify a desktop paste.

The initial mouse failure exposed a transport bug, not a mouse codec bug.
Before the fix, the captured native stream stopped at 77,893 bytes, partway
through a 96,386-byte initial surface frame. Sending unrelated input caused the
remaining bytes to arrive. `tokio::io::copy_buf` flushes at EOF; the Herdr source
stays open and idle, so buffered TLS output could remain unwritten. The bridge
now uses bounded `tokio::io::copy`, which also flushes when the source becomes
idle. A regression using the real TLS implementation and a passive receiver
failed at its two-second deadline before the change and passed after it. The
real Cloudflare run then received the full initial surface before sending paste
or mouse input. No native frame is parsed or rewritten by this fix.

A separate native local bridge check exposed the normal-detach EOF racing the
client's successful exit. A confirmed successful native exit now resolves that
specific `CONNECTION_LOST` race; abnormal exits and other errors retain their
failure semantics. The original manual scenario passed after the change.

Existing opaque 512 KiB, bidirectional 1 MiB, credit-window and terminal cleanup
regressions remain. See [flow control](2026-10-10-flow-control.md) for sustained
output, stalled readers, isolation and the upstream queue limitation, and the
reconnection evidence for discarding offline input. Those resource limitations
remain release constraints; this terminal check does not supersede them.

Visual terminal acceptance remains incomplete. Ghostty 1.3.1 was identified,
but computer-use access was denied by the tool's safety check. No screenshot or
visual/click test was performed, and no alternate UI-control route was used.
The table records PTY and native protocol evidence, not a claim that Ghostty's
rendered fonts, image appearance, mouse interaction or OS clipboard were seen.
Other terminal programs and physical Intel Mac rendering are unverified.
