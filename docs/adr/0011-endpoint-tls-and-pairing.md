# ADR-0011：端点 TLS 与一次性配对方案

日期：2026-10-09；更新：2026-10-10。状态：**TLS 身份与原子配对已实现，Workers 本地、受控云端与四平台候选路径已有验证**；完整发布验收仍未完成，具体运行环境及缺口见[候选记录](../validation/2026-10-10-candidates.md)。它细化已确认的端到端加密和设备配对要求，不代表用户选择过某一密码库。

实现采用锁定的 rustls 0.23.45 / ring 0.17.14、Ed25519 SPKI 固定与 WebPKI 握手签名验证。证书 profile、缓冲与超时上限、CLI 手动结果和必要测试见[本地 TLS 验收](../validation/2026-10-10-device-tls.md)。这一证据支持后续实现采用该方案，不等于四平台验收或公开服务已经完成。

邀请默认有效期 10 分钟，秘密 256 bit，原设备/请求/秘密可在提交后 24 小时内取回原结果。邀请消费与方向授权在同一私有快照事务落盘后才回复；验证记录见[本地配对](../validation/2026-10-10-local-pairing.md)和 [Workers 本地及真实部署配对](../validation/2026-10-10-cloudflare-pairing.md)。

## 方案与依据

优先验证 rustls 提供的 TLS 1.3，在两个 Rust 端点之间通过 Relay 字节流建立内层 TLS；外层 WSS 继续使用普通服务器证书校验。内层采用设备公钥固定与双向身份验证，Cloudflare 不终止内层 TLS。

rustls 提供独立的证书验证和握手签名验证接口；自定义公钥信任策略仍必须验证 CertificateVerify，不能返回无条件成功。[服务端证书验证接口](https://docs.rs/rustls/latest/rustls/client/danger/trait.ServerCertVerifier.html)、[客户端证书验证接口](https://docs.rs/rustls/latest/rustls/server/danger/trait.ClientCertVerifier.html)

本次阅读的 API 文档显示 rustls 0.23.45；实施时锁定实际依赖、provider 和版本，再按该版本核对接口。Context7 的 main 分支示例不是版本锁定依据。选用成熟 TLS 实现也不意味着本项目的公钥固定、配对和撤销已经受到审计。

## 身份与信任

- 一个本机用户配置拥有一份设备身份，不按每次 CLI 进程重新生成；不同 OS 用户互不共享私钥。
- 设备 ID 由身份公钥指纹导出。内层证书 SPKI 与保存的设备公钥绑定，设备名称仅供显示。
- 配对串携带协议版本、Relay origin、发布方身份公钥或其固定指纹、邀请 ID、随机兑换秘密和有效期。兑换秘密至少 256 bit；传递配对串的渠道承担首次信任引入。
- 当前身份密钥使用 Ed25519。四个目标均已运行证书生成与握手路径，证书 profile 和校验见 TLS 验收；不提供自动身份密钥轮换，不能临时改成接受任意证书。
- 首版不开放 0-RTT，不复用 TLS 会话恢复票据；每次重连重新验证双方身份和最新授权。稳定公钥下的证书更新与身份密钥更换分开处理；换身份需重新配对。
- 私钥文件仅本机用户可读，目录 `0700`、文件 `0600`；不存入仓库或 Cloudflare。丢失私钥后建立新身份，旧身份由其他发布方撤销，不提供云端找回。

## 配对事务

1. A 后台服务生成邀请，持久保存邀请 ID、秘密摘要、有效期和未使用状态。默认有效期建议 10 分钟；可主动作废。
2. B 通过交互输入或标准输入导入配对串，先固定 A 身份，再建立只允许配对的内层 TLS 通道。秘密不进入 URL、命令行参数、诊断日志或 Relay 明文消息。
3. 配对入口允许尚未授权的 B 提供自签设备证书，但必须检查证书结构、算法约束和握手签名以证明私钥持有；此阶段只能提交配对请求，不能列目标或打开 Herdr socket。正常访问入口必须命中现有公钥授权。
4. B 在加密连接中提交邀请 ID、秘密和持久化的 `request_id`。A 将请求绑定到当前已完成握手的 B 公钥，原子提交“邀请已使用 + A 授权 B”后才返回成功。
5. 返回丢失时，只允许同一 B 身份、同一请求 ID 和秘密在有限保留期内查询原结果，不能借此第二次授权。B 收到成功后持久保存 A 的身份与该方向授权，再发送加密 request_id 确认；A 等待确认后关闭通道，避免中继提前关闭丢弃结果。失败不显示成功。
6. 并发兑换只能有一笔提交成功。A 重启后仍依据已落盘状态判断；A 离线则不能完成兑换。Herdr 不参与此事务。

兑换接口的宽松初始信任必须与正常连接代码路径隔离。错误对外可统一为 `PAIR_INVALID`，详细原因仅在本机提供；已用秘密和结果记录到期清理。授权本身默认持续到显式撤销，不随邀请到期失效。

## 正常访问与撤销

内层握手后，两端交换加密的通道上下文：Relay origin、双方 device ID、用途、目标 ID、`channel_id` 和发布方启动代次。必须与各自预期一致。A 在拨本地 socket 前检查最新方向性授权和目标 enabled 状态。

撤销先在 A 本地持久化并更新授权代次，再关闭 B 对 A 所有目标的连接；同步云端拒绝旧接入票据。离线期间发生的撤销也要在恢复服务时先应用，再接受连接。云端仍持有旧路由或票据不应绕过 A 的检查。反向授权单独存储，不被连带删除。

设备到 Relay 的接入证明只负责云端路由和资源准入。云端可拒绝、延迟、断开或观察流量元数据，但不得因掌握路由凭据而冒充任一已固定身份的端点。TLS 失败立即断开，不回退明文。

## 必须通过的验证

- 错误主机指纹、错误客户端身份、假签名、畸形证书、协议降级均被拒绝。
- Relay 替换公钥、串线到另一目标、修改上下文或重放密文时，端点不能继续访问。
- 配对请求并发、超时、断线重试、写盘失败及提交后重启，均不形成两份授权。
- 撤销与正在握手、待开通、活动连接和自动重连竞争时，撤销生效。
- 禁用会话恢复和 0-RTT 的配置在锁定依赖版本上有实际测试；证书更新不能绕过公钥固定。
- 跨 macOS/Linux 与两种架构完成内层 TLS，验证缓冲上限和 CPU 成本。

这些是公开服务前的实现门槛，不要求用户再次确认既有产品范围。若 P1 无法满足，应修改本提案并记录原因，不能削弱验证后继续发布。
